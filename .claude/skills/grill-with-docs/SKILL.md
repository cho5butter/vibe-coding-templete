# grill-with-docs

ドキュメント・既存仕様・ユーザー提示資料の曖昧さを徹底的に深掘りし、後工程で発覚する手戻りを未然に防ぐためのスキル。

仕様駆動開発（SDD）の **要件定義フェーズ** と **設計フェーズ** で必ず活用すること。プロジェクト原則の詳細は `spec/workflow.md` の「プロジェクト原則」セクションを参照。

## 起動方法

```
/grill-with-docs <対象ドキュメント or トピック>
```

引数なしで起動された場合は、現在フェーズ（`spec/status.md` 参照）に応じて以下を対象とする。

- 要件定義フェーズ: `spec/requirements.md`、およびユーザー提示資料
- 設計フェーズ: `spec/design.md`、および要件定義で確定した内容

## いつ使うか

| フェーズ | 使うタイミング | 重点的に引き出す観点 |
|---------|---------------|--------------------|
| 要件定義 | ユーザー提示資料を読んだ直後、要件確定前 | 目的・スコープ・受け入れ基準・ユビキタス言語・非機能要件 |
| 設計 | 要件確定後、設計初期案作成中 | 制約・トレードオフ・代替案・境界づけられたコンテキスト・脅威モデル |

**実装フェーズ・計画フェーズでは使わない**（フェーズゲート違反）。

## 進め方

1. **対象を特定する** — ドキュメント or トピックを明示し、ユーザーと合意する
2. **観点別に質問を起票する** — 下記「質問テンプレート」から該当フェーズの観点を選び、対象の曖昧箇所をリストアップ
3. **質問を 1 ラウンドあたり 3〜5 件にまとめる** — 一度に大量に出さず、優先度の高いものから順にユーザーに提示
4. **回答を該当ドキュメントに即反映する** — 口頭で得た合意を `spec/requirements.md` / `spec/design.md` に書き戻す（ユーザー合意の上で）
5. **曖昧さが残っている限り 2〜4 を繰り返す** — 「これ以上深掘りすべき点がない」とユーザーと合意するまで止めない

質問は `AskUserQuestion` ツールで提示することを推奨する。複数選択肢を提示できる質問に整形すること。

## 質問テンプレート

### 要件定義フェーズで使う観点

#### 目的・背景
- なぜ今これを作るのか／作らない場合に何が起きるのか
- 既存の代替手段はあるか／なぜそれでは不十分か
- ステークホルダーは誰か／成功判定は誰が行うか

#### スコープ
- 含めるもの／含めないものはそれぞれ何か（明示的に列挙）
- MVP の境界はどこか／将来のフェーズに送るものは何か
- 対象ユーザー層・対象環境（OS / ブラウザ / 言語 / 地域）は何か

#### ユーザーストーリー・ユースケース
- 主要なユーザー（ペルソナ）は誰か／各ペルソナの主要シナリオは何か
- 異常系・エッジケースのシナリオは何か（権限不足・通信断・データ不整合 等）

#### 機能要件
- 各機能の優先度は何か（Must / Should / Could / Won't）
- 機能間の依存関係はあるか
- 入力・出力・前提条件・事後条件は何か

#### 非機能要件（NFR）
- パフォーマンス: **画面表示 100ms 以下** はデフォルトで含めること（達成困難な処理は楽観的UI・スケルトン等で知覚レイテンシを下げる）
- セキュリティ: **OWASP Top 10** の各カテゴリでリスクを列挙すること
- 可用性・スケーラビリティ・国際化・アクセシビリティ・監視・ロギング

#### 用語定義（ユビキタス言語）
- 主要な概念に対する一意な日本語／英語名は決まっているか
- 同義語・別表記は許容するか／禁止するか
- 用語集は `spec/requirements.md` に集約する（DDD のユビキタス言語の起点）

#### 受け入れ基準
- 各機能要件に対し、検証可能な受け入れ基準（Given-When-Then 等）があるか
- ユーザー自身が「OK」と判断するための観測可能な条件は何か

### 設計フェーズで使う観点

#### 制約
- 技術的制約（既存システム・予算・期間・チームスキル）は何か
- 法規制・契約上の制約はあるか
- 既存資産との互換性要件はあるか

#### トレードオフ
- 一貫性 vs 可用性／レイテンシ vs スループット／開発速度 vs 拡張性
- どちらを優先するかの判断軸は何か（要件のどの NFR に紐づくか）

#### 代替案
- 採用案以外にどの選択肢を検討したか／なぜ採用しなかったか
- 採用案のリスク・撤退条件は何か
- ADR（Architecture Decision Record）として記録する

#### DDD
- 境界づけられたコンテキストの分割案は妥当か／コンテキストマップに矛盾はないか
- 集約境界はトランザクション境界と一致しているか
- レイヤー分離（プレゼンテーション/アプリケーション/ドメイン/インフラ）が守られているか／ドメイン層がフレームワーク・DB に依存していないか

#### セキュリティ設計（OWASP Top 10）
- 認証・認可方針は明示されているか／認可は誰がどの粒度でチェックするか
- 入力検証・出力エスケープのレイヤーはどこか
- 機微情報の保管・転送・ログ出力の扱いは明示されているか
- 外部システム連携時の SSRF・XXE 対策はあるか
- 既知脆弱性のあるコンポーネントの監視（Dependabot 等）が設計に組み込まれているか

#### パフォーマンス
- **画面表示 100ms 目標** をどの戦略で達成するか（キャッシュ・楽観的UI・スケルトン・バックグラウンド処理・CDN・SSR/SSG 等）
- 達成困難な箇所は ADR に理由とともに記録されているか

#### データモデル
- エンティティ・値オブジェクト・集約の責務分割は妥当か
- 状態遷移（ステートマシン）が明示されているか
- データ整合性ルール（一意性・参照整合性・履歴保持）は明示されているか

#### エラーハンドリング
- エラー分類（システム/業務/ユーザー入力）と対応方針が明示されているか
- ユーザーに見せるエラーメッセージのトーン・粒度は決まっているか

## 完了条件

このスキルの 1 セッションは、以下のいずれかで完了とする。

- ユーザーと「これ以上深掘りすべき点がない」ことを明示的に合意した
- 当該フェーズの完了条件（`spec/workflow.md` 参照）を満たした

完了したら `spec/status.md` の「直近の状況」「次のアクション」を更新すること。

## やってはいけないこと

- 推測で要件・設計を確定する（必ずユーザーに確認する）
- 実装・計画フェーズで起動する（フェーズゲート違反）
- ユーザー合意なく `spec/` 内のファイルを変更する
- 質問を 1 ラウンドで大量に詰め込む（3〜5 件ずつ、優先度順に）
- 100ms 目標・OWASP Top 10・DDD の 3 原則のいずれかを質問観点から外す
